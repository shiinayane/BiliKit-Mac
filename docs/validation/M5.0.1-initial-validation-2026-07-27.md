# M5.0.1 首轮验证记录

日期：2026-07-27（Asia/Tokyo）

范围：根视图对象身份、统一 HLS 媒体语义、真实媒体／字幕准备时序。未修改生产代码，
未保存 BVID、CID、标题、字幕正文、远端 URL、Cookie、原始响应或现场 xcresult。

## 1. 根视图 model/player identity

无网络测试保持同一 `NSHostingView<AppRootView>` 的结构身份，再以两套 environment
依次重建 root。结果为：

- 播放请求仍进入第一套被 `@State` 保留的 model/player；
- 播放器表面来自第二次 initializer 的普通 `playerContent`；
- suite xcresult：2 tests，1 passed，1 expected failure，0 unexpected failure；
- 证据 bundle（临时）：`/private/tmp/bilikit-root-suite.uqvNgi/root-suite.xcresult`。

结论：STATE-001 的脱节不是纯静态猜测。应替换 root 的 environment 构造方式；在生产
修正前测试保留为 expected failure。

## 2. 统一 HLS master

本地 synthetic AVC/AAC 与内存 WebVTT 通过 loopback server 组成同一 HLS master：

- 两个 `EXT-X-STREAM-INF`；
- 一个独立 audio group；
- 一个 `DEFAULT=NO`、`AUTOSELECT=NO` 的 subtitle group；
- variant 含 `BANDWIDTH`、`AVERAGE-BANDWIDTH`、`RESOLUTION`、`FRAME-RATE` 与
  `CODECS`。

2026-07-27 追加第二份独立 synthetic AVC fixture 后，两个 variant 分别为：

- 128×72、H.264 Main@L1.0、variant bitrate 146 kbps；
- 256×144、H.264 Main@L1.2、variant bitrate 196 kbps。

`AVURLAsset` 实际读取到两个 bitrate、两种 presentation size 与 24 fps；`.legible`
group 有一项，默认关闭，显式选择后成为当前 media option。master 故意把高档放在前面：

- `preferredMaximumResolution = 128×72` 时，access log 实际出现 146 kbps；
- `preferredMaximumResolution = 256×144` 的独立 item，access log 实际出现
  196 kbps。

定向测试和完整 9 项 loopback suite 均通过。

限制：这证明 AVFoundation 能按 item 的分辨率约束选择两份真实不同编码尺寸的 variant；
运行时约束行为见第 5 节。仍不证明真实网络下的自动升降档策略。

## 3. 真实字幕相对媒体截止点

签名探针在取得播放 identity 后，同时启动：

- playback endpoint、视频/音频 SIDX 与 loopback HLS media assembly；
- WBI 字幕目录、选定轨道正文与生产 decoder。

单次脱敏结果：

```text
relation=subtitle-after-media
media=250-499ms
subtitle=500-999ms
tracks=2
cues=838
kind=standard
cleanup=complete
```

探针结束后清理临时 BVID 注入、日志、DerivedData 与 xcresult。

结论：

- 旧 spike 的截止冲突真实存在：不等待时，本次字幕会错过 master 冻结；
- 本次正文仍在共同起点后一秒内完成，说明“有限等待换原生字幕”值得继续验证；
- 一次现场成功不能确定生产等待预算，也没有证明 automatic 轨、弱网、多个正文并发或
  不同清晰度 master。

## 4. 有界等待与冻结状态机

2026-07-27 追加 test-only async spike，不使用固定 sleep，以可控 subtitle/deadline
stream 表达 media cutoff 后的 grace window。覆盖：

- 字幕在 media cutoff 前完整完成：立即纳入，deadline waiter 被取消；
- 字幕在 grace window 内完成：纳入本次 frozen set；
- deadline 先到：本次明确无字幕，之后的正文提交得到 terminated；
- 页面/加载取消：subtitle 与 deadline 两个 waiter 都取消；
- generation 20 被 generation 21 替换：旧 continuation 不能提交，新 generation
  可以正常纳入。

定向 SwiftPM 结果为 5/5 通过。它证明冻结、迟到丢弃和取消语义可以由一个 load-scoped
owner 表达，不证明生产代码已经具备这些语义，也不决定具体 grace duration。

当前调用图给出的 owner 结论：

- Application/Feature 只能在 BVID/CID identity 已知后启动字幕目录与正文准备，因为只有
  该侧能访问 `SubtitleUseCase`；
- master 暴露、player item、load generation 与 stop/replace 已由 `AVPlayerEngine` /
  `DASHToHLSBridge` 链路拥有；
- 因此 production 不能让 `SubtitleViewModel` 和 player 各自加载一次。应把一个纯值、
  可取消的 subtitle preparation 输入交给播放 load；字幕准备与媒体 bridge 并行，
  media cutoff 后由同一 load task 执行一次 grace/freeze，再一次性注册 master；
- 具体 freeze 函数可位于 bridge 内部，但取消、generation 和最终 asset 生命周期仍由
  `AVPlayerEngine` 单一拥有。

追加 test-only master commit 验证：

- media-only master 进入 ready 后，AVFoundation 的 `.legible` group 只有系统合成的
  `CC` 项，没有 WebVTT 轨；
- 随后成功注册 subtitle playlist 与 WebVTT 两条 route，server route count 增加 2；
- 已发布 master 的响应 bytes 完全不变；
- 原 asset/item 的 legible options 也完全不变，没有出现迟到 WebVTT 轨。

因此“route 存在”和“字幕被 master 暴露”是两个不同事实。deadline 路径只要先冻结并发布
media-only master，迟到结果就不能半途加入原 item；生产接入时仍应避免无意义地注册迟到
route，并由同一个 load owner 在取消或替换时停止 server。

## 5. 同一 item 的运行时分辨率约束

SDK interface `AVPlayerItem.h` 将 `preferredMaximumResolution` 定义为 HLS 下载与渲染的
“preferred upper limit”；`startsOnFirstEligibleVariant` 只影响初始 variant，且明确说明
AVPlayer 播放中仍可能切换 variant。它们都没有承诺“选择指定清晰度”。

追加四秒、四个一秒 fragment、单个 global SIDX 的 synthetic 资源：

- 128×72 H.264 Main@L1.0；
- 256×144 H.264 Main@L1.2；
- 独立静音 AAC；
- `DEFAULT=NO` 的 WebVTT subtitle group；
- test-only Range transport 每次响应增加 150 ms 有界延迟，并把
  `preferredForwardBufferDuration` 设为 1 秒，避免本地 loopback 一次预取完整 VOD。

确定性结果：

- 同一个 item 先以 256×144 上限启动，access log 出现 132 kbps；
- 播放中将上限收紧到 128×72，随后同一 item 出现新的 82 kbps event；
- `player.currentItem` 身份未改变；
- 已选择的 WebVTT media option 在降档后保持不变。

反向 spike 的结果不同：从 128×72 放宽到 256×144 后，在同一十秒 synthetic 播放中没有
出现高档 event。这个结果与“上限只扩大候选集”一致，但单次未升档不能证明 AVPlayer 永远
不会自动升档。

结论：

- 原生 API 足以在不替换 item 的情况下收紧上限并强制降档；
- 放宽上限不等于命令升档，升档仍由自适应算法决定；
- 如果产品的“清晰度切换”表示精确指定某档，不能只暴露
  `preferredMaximumResolution` 并宣称已经实现手动清晰度选择；
- 若产品接受“自动／最高允许分辨率”，则可保留同一 item、原生 ABR 和原生字幕。

## 6. B 站服务侧 4K capability matrix

使用一个由当前 OSS 标注为 4K 的公开普通视频，只发出一次 view 与两次匿名非 WBI
playurl 请求。探针只投影 HTTP/业务状态、画质编号、权限字段和 DASH codec/尺寸聚合；
临时响应以 mode 600 保存于系统临时目录并在进程退出时删除。未记录视频身份、CID、URL、
Cookie、标题或原始响应。

| 匿名请求形态 | HTTP／业务 code | selected quality | `accept_quality` | 实际 DASH |
| --- | --- | --- | --- | --- |
| 当前 `qn=32/fnval=16/fourk=0` | 200／0 | 32 | 112, 80, 64, 32, 16 | 32/16；AVC＋HEVC |
| 高画质 `qn=120/fnval=976/fourk=1` | 200／0 | 64 | 125, 120, 112, 80, 64, 32, 16 | 32/16；AVC＋HEVC |

结论：

- B 站 endpoint 的能力目录对该内容明确识别 quality 120（4K），所以“B站侧没有 4K”
  可以否决；
- 匿名请求虽声明 4K，仍没有获得 quality 120 representation，因此不能把
  `accept_quality` 或 selected quality 当成实际可播放流；
- 当前 BiliKit 固定 `fourk=0`、只保留 AVC、再只选择一个 representation，生产能力
  明确尚未覆盖 4K；
- 普通登录与会员身份仍待验证。现有 `BiliCredentialRequestAuthorizer` 精确 allowlist
  不允许 playurl；本轮按安全约束停止，没有为探针放宽 Cookie 发送范围。该矩阵应在
  authenticated playurl endpoint/query 与 allowlist 正式裁决后继续。

## 7. 真实音视频 SIDX 结构

继续使用同一个公开匿名样本，从当前 playurl 返回的 AVC 视频与 AAC 音频各选择一个
representation，只请求 endpoint 声明的 `index_range`。两个 CDN 均返回 HTTP 206；
输出只保留结构数值，临时媒体字节以 mode 600 保存并在进程退出时删除。

| 轨道 | SIDX 形态 | timescale | EPT | references／SAP | 首段 | 索引总时长 |
| --- | --- | ---: | ---: | --- | ---: | ---: |
| 视频 | v0、单 box、size 与响应相等 | 16000 | 0 s | 61 direct／61 type 1 | 5.005 s | 304.704 s |
| 音频 | v0、单 box、size 与响应相等 | 48000 | 0 s | 61 direct／61 type 1 | 4.992 s | 约 304.768 s |

这份现场结构落在当前 `SIDXParser` 支持的 direct v0 子集内，并且音视频都从 EPT 0
开始；两轨索引总时长相差约 64 ms。它缩小了“当前算法完全不符合真实 B 站媒体”的风险，
但只是一份匿名低画质样本，不能证明 v1、large-size、额外 box、不同 EPT 或更大边界差
不会出现，也不能代替真实首播/seek 后的音画偏移测量。

## 8. 精确清晰度的 item 替换

新增 test-only AVPlayer 对照，继续使用两份不同分辨率的四秒 synthetic AVC、共享 AAC、
默认关闭的 WebVTT，以及每次 Range 固定延迟 150 ms 的 loopback transport。它不修改
production engine。

单 player 路径先在旧 item 播放中预加载新 asset 的 playable/duration/legible metadata，
然后暂停、`replaceCurrentItem`、等待新 item ready、精确 seek 到旧位置、恢复播放并显式
恢复字幕。最终连续五次结果：

| 指标 | 区间 |
| --- | ---: |
| 替换到首个 decoded video frame | 625–638 ms |
| 替换到时间线重新前进 | 743–757 ms |
| 恢复后的时间位置误差 | 58–62 ms |

因此这一路径位置和字幕可以恢复，但稳定存在超过半秒的媒体空档，不能称为用户感知无缝。
当前 `AVPlayerEngine` 还会在准备新 asset 前先清空旧 item/server，实际设计只会比该
test-only 最佳单 player 路径更弱。

另一个预热尝试把新 item 放入 staging player、seek/preroll 后再转交原 player；
AVFoundation 以 `NSInvalidArgumentException` 终止。Xcode 26.6 `AVPlayer.h` 也明确说明
已关联到另一个 player 的 item 会触发异常，因此这不是可继续打磨的受支持方案。

保留 item 在第二个 player 的对照则可运行：最终五次后台准备为 484–509 ms，候选交接点
两条时间线相差 75–82 ms，新 item 已有 decoded frame，字幕也已选择。准备延迟可以藏在
旧画面继续播放期间，但本轮没有真正切换两个 `AVPlayerLayer`/`AVPlayerView`，也没有测
音频输出或双份资源峰值。

随后补充的当前实现调研没有发现“B 站 Web 正在使用双 player”的证据。匿名公开页面只有
一个 `<video>`；普通 DASH 清晰度通过 dash player/MSE fast representation switch，并等
`QUALITY_CHANGE_RENDERED` 后更新状态。只有 whole-source 重建路径会用旧帧 canvas 遮住
video，等 `canplay` 后移除。三个活跃 OSS 也分别采用：

- cilicili `6f02857`：同 item bitrate 切换，或预热缓存后用旧帧 snapshot 遮罩新 player
  首帧；
- ATV-Bilibili-demo `86ba6f5`：新建 AVPlayer、直接替换、seek/play；
- wiliwili `88e5876`：mpv `loadfile ... replace`。

这意味着双 player 仍是合理实验候选，却不能因 Web 的视觉观感或 OSS 先例直接判定为
已验证方案。“加载完全”也不应理解为下载完整视频，而至少应同时满足目标 seek/preroll、
新 surface 首帧可显示、时间线进入容差、字幕恢复和交接前静音。因此当前裁决是：

- 单 player item 替换：明确不能作为“无缝”实现；
- 双 player／双 surface 交接：有继续验证价值，但尚未证明用户无感；
- snapshot 遮罩：已有 B 站 Web whole-source 与 cilicili 的实现先例，可作为低成本对照，
  但它只隐藏黑帧，不证明音视频连续；
- 若未来恢复精确手动画质，必须先测真实 rendered surface、音频 discontinuity、失败回滚
  和资源峰值，不能仅凭 decoded frame ready 进入生产。

2026-07-27 后续产品裁决进一步收窄 V1：只提供自动画质，不提供手动清晰度档位。V1
优先把真实可用的多个 representation 正确组装进同一 Apple-profile multivariant HLS
item，由 AVPlayer ABR 无感选择；MP-012 的双 player/snapshot 方案不再阻塞 V1，也不继续
投入实现。未来出现明确的精确档位需求时，再依据本节证据重新打开验证。

本轮最终 `package` gate 通过：静态契约、架构边界、秘密模式、工程配置、Swift 格式与
Swift Package 全部通过，共 214 tests／36 suites。追加 ABR 探针后再运行最高层
`app` gate，App 无签名 build-for-testing 与 App unit tests 同样通过；需要显式 BVID 的
两项真实网络 probe 在普通 gate 中按设计跳过。

## 9. V1 自动画质／原生 ABR

V1 产品裁决为只提供“自动”画质后，ABR 成为主播放路径，因此在审计阶段增加两层
test-only 验证，没有修改 production bridge。

第一层使用两份不同分辨率的四秒 synthetic AVC、共享 AAC、同一个
`AVPlayerItem` 和实际 `AVPlayerLayer`：

- 初始 access log 观察到 132 kbps 高档；
- test transport 限制高档交付后，同一 item 自动出现 82 kbps 低档；
- 高、低两份媒体都确实收到 Range 请求；
- 连续 6/6 通过，item identity 始终未替换。

这证明 AVPlayer 的原生 ABR 降档能穿过 BiliKit 的 loopback/HLS 形态。恢复实验没有得到
可信升档：人工 transport 对高档单独施加慢响应／挂起，AVPlayer 即使在低档观察到充足
吞吐也没有在观察窗口内重试高档。该模型不是均匀网络整形，可能触发 representation
惩罚或 hysteresis，因此只能记作“恢复升档尚未建立”，不能记作产品缺陷。

第二层复用签名脱敏探针，读取一个公开匿名样本实际返回的两档 AVC SIDX：

```text
qualities=2
low=16 high=32
references=466/466
start=aligned
duration-delta=under-1ms
maximum-boundary-delta=under-1ms
sap=all
cleanup=complete
```

Apple HLS Authoring Specification 要求 VOD playlist 覆盖相同媒体时间范围，并建议所有
variant 的 segment boundary 位于相同时间点；本样本的 reference 数一致、均从 SAP
开始，累计差低于 1 ms，结构上支持继续组为 switching set。它仍只是一条匿名、低画质、
单次样本，不证明 4K、其他视频、真实升降档或 `BANDWIDTH`/`AVERAGE-BANDWIDTH` 正确。

当前 production 尚无 ABR：`DASHToHLSBridge` 仍只接收一个视频 representation，
`MediaRepresentation` 也没有保留远端 width、height、frameRate，无法生成完整 Apple
profile multivariant 元数据。因此本轮结论是“方向可行且值得进入实现路线”，不是
“自动画质已完成”。

随后增加第三层签名 test-only 真实播放验证。探针把上述 quality 16/32 两档与共享 AAC
实际注册到同一 loopback master，并为全部音视频 Range 使用一个动态共享吞吐模型：
在途响应每 100 ms 按当前总带宽重新分配吞吐，恢复带宽会立即加速旧请求，不会只惩罚
某一个 representation。

最终脱敏结果：

```text
variants=2
initial=high
downgrade=observed
recovery=not-observed
recovery-window=45s
metadata=recognized
same-item=true
cleanup=complete
```

恢复阶段的总吞吐设为高档声明 `BANDWIDTH` 的 4 倍；观测器检查 access log 中最后一个
有效 `indicatedBitrate`，不依赖 event 数量递增，因此不受旧 event 被裁剪影响。由此可
确认：

- 真实 B 站双档媒体能够在同一 item 中由 AVPlayer 自动降档；
- 自动降档不需要 item 替换、双 player 或手动清晰度状态机；
- 该样本恢复高带宽后 45 秒内没有升档，V1 不能承诺固定时间恢复最高档；
- 随后从同一次 playurl 响应仅在 test transport 内存提取两档真实
  width/height/frameRate，写入 master，并确认 `AVAssetVariant.videoAttributes`
  识别对应尺寸与帧率；相同路径的恢复结果仍为 45 秒内未升档；
- 因此尺寸/帧率不是该样本恢复升档的缺失开关，但 API bandwidth 仍未证明等于 Apple
  HLS 所需 peak/average 语义，且 AVPlayer 没有公开精确升档命令或时限保证。

因此 MP-001 的“原生自动画质方向”已经越过可行性门槛；进入生产前剩余的是完整元数据、
带宽计算、Apple validator 与最终实现回归，而不是重新设计播放器切换架构。恢复升档
不再阻塞 V1：保持 `preferredPeakBitRate`、`startsOnFirstEligibleVariant` 和 buffer
策略的系统默认值，不加入定时升档或其他恢复 workaround；未来有真实体验需求再重开。

## 10. 原生字幕正文按需加载

2026-07-29 在既有 unified master spike 上增加 loopback 请求计数，没有接触真实字幕
内容或认证请求。测试使用两档视频、共享音频、`DEFAULT=NO` 的 WebVTT rendition 和同一
`AVPlayerItem`：

1. item ready 后保持字幕未选择，实际播放到 0.15 秒，WebVTT 正文 GET 为 0；
2. 选择 `.legible` option 后，AVFoundation 才发起 WebVTT 正文 GET；
3. 原生轨道仍默认关闭，item 没有因为选择字幕而替换。

这证明 master 只需在发布前冻结字幕**目录和 playlist**，不必为了默认关闭的字幕在首播
