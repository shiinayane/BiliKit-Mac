## 确定性 Gate

Apple UI preflight 在沙箱内首次停在 `xcodebuild -list`；同一只读命令在获准的本机环境
复核后为 0 failures、0 warnings，工程、`BiliKitMac` scheme 和 Xcode 26.6 均可用。

最高适用 Gate：

```sh
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
BILIKIT_COMPACT_LOGS=1 \
BILIKIT_DERIVED_DATA_PATH=<private-stage10-derived-data> \
sh Scripts/run-quality-gates.sh app
```

首次沙箱执行在 SwiftPM manifest 编译前因用户 ModuleCache 不可写而失败，分类为
`sandbox`，没有产品 assertion 执行。Stage 10 修改签名契约后又曾因 UI 测试文件的 strict
Swift Format 失败一次；格式化该文件后，使用 fresh DerivedData 在获准本机环境重跑：

- static contracts：通过；
- Swift Package：226 tests／36 suites 通过；
- App build-for-testing：通过；
- App unit tests：通过；
- 最高 `app` Gate：通过。

最终 Gate 使用 `com.shiinayane.BiliKitMac.dev`，并要求该当前开发标识在 App Debug／Release
中恰好声明两处，同时检查动态 Keychain access group。该约束有意保持简单：取得正式开发者
账号并更换标识时，必须在同一个可 review 的变更中显式更新工程值和静态契约，再重跑签名
验证。它不尝试在 shell 中重新实现 OpenStep plist 解析器。完整日志只保留在本机私有临时
目录，完成记录后按 artifact 规则清理，不是仓库长期 artifact。

App 测试实际覆盖：

- coordinator 的单层播放 destination、系统 pop、来源恢复与替换语义；replacement 只交给
  `GuestVideoViewModel.loadVideo` 执行 generation、取消和旧 playback stop，不经过仅供退出的
  完整 reset；
- `PlayerHostViewIdentityTests` 对实际 `AVPlayerView` 数量和 `ObjectIdentifier` 的遍历；
- `VideoDetailLifecycleTests` 通过生产 coordinator 的 A → B、失败、retry 与 Back 顺序，确认
  同一个实际 `AVPlayerView` 只在退出目的地时拆除并断开 player；
- `UITestLocalAVPlayerPlaybackTests` 对真实本地 `AVPlayerItem`、generation、observer、准备期
  取消和临时媒体目录清理的检查；
- Browse／History、字幕、弹幕、loopback 和窗口关闭的既有回归测试。

build-for-testing 证明当前 XCUI target 和 fixture 可以编译；它不证明 runner、系统控件或
签名环境实际执行了测试。

## signed XCUI 结果与签名边界

Step 9 首次使用原 Bundle Identifier 和 fresh DerivedData 运行三条 contextual navigation
XCUI，未设置 `CODE_SIGNING_ALLOWED=NO`。该次命令在 build 阶段以 exit 65 结束，原始关键
错误为：

```text
No profiles for 'com.shiinayane.BiliKitMac' were found: Xcode couldn't find any
Mac App Development provisioning profiles matching 'com.shiinayane.BiliKitMac'.
Automatic signing is disabled and unable to generate a profile. To enable automatic
signing, pass -allowProvisioningUpdates to xcodebuild.
```

该次结果 bundle 完成归因后已清理。没有 XCUI test case 进入用户路径，因此该次失败分类为
`signing`，不能记为 assertion 通过或产品失败。

随后没有增加 `-allowProvisioningUpdates`，因为该选项可能获取或生成开发 provisioning
profile 并改变 Developer Portal 外部状态。该阶段没有修改 `.pbxproj`、Team、Bundle ID
或本机签名配置，也没有可归因于迁移代码的账号／Portal 状态变更或残留 profile。

之后当前开发 Bundle Identifier 临时固定为 `com.shiinayane.BiliKitMac.dev`；该工程配置
使 Xcode 能使用本机已有开发签名环境。Stage 10 没有更改 Team、profile 或 Portal，也没有
使用 `-allowProvisioningUpdates`。Keychain access group 随后改为从
`$(PRODUCT_BUNDLE_IDENTIFIER)` 派生，使将来更换正式开发者账号／标识时继续由静态契约
检查 Debug／Release 与 entitlement 一致。签名恢复仍是环境／工程标识边界的变化，不是
`NavigationSplitView` 产品代码修复；新标识也不继承旧 access group 的登录态。

在该签名边界下，使用 Xcode 26.6、fresh DerivedData 和真实 macOS XCUI runner 运行：

```sh
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer \
xcodebuild -project BiliKitMac.xcodeproj -scheme BiliKitMac \
  -destination 'platform=macOS' \
  -derivedDataPath <private-stage10-derived-data> \
  -resultBundlePath <private-stage10-result-bundle> \
  test \
  -only-testing:BiliKitMacTests/SignedKeychainSmokeTests/testDataProtectionKeychainAddUpdateReadDelete \
  -only-testing:BiliKitMacUITests/BiliKitMacUITests/testContextualNavigatorReturnsEachSourceAndRestoresSearchDraft \
  -only-testing:BiliKitMacUITests/BiliKitMacUITests/testContextualReplacementUsesRealLocalPlayerAndCleansOnBack \
  -only-testing:BiliKitMacUITests/BiliKitMacUITests/testContextualSidebarScrollIdentityAcrossPartBVIDAndWindowSizes
```

最终结果：4 tests／0 failures、0 skips，包含 1 条 signed Keychain smoke 和 3 条 signed
XCUI，分类为通过。构建产物的 application identifier、首个 Keychain access group 和
Bundle Identifier 后缀也实际一致。测试覆盖：

- 隔离测试 service/account 的 Data Protection Keychain add、read、duplicate → update、
  read、attribute 检查、delete 和删除后 nil；测试开始前与 `defer` 均清理；

- 系统 Back 对热门、搜索和显式 UITest 历史来源的返回；三份来源均先滚动至末端 marker，
  返回后 marker 仍可交互，搜索 draft 保持，且对应 repository 请求计数没有增加；
- sidebar hide／show、同 BVID 分 P、A → B → C 原位媒体替换、单层 Back 与窗口关闭清理；
- 本地真实 `AVPlayerItem` 时间线推进，player／item identity、generation 和 observer 状态；
- 窗口先主动建立为 1320×820，再由 XCUI 边缘拖动到 1080×680；自动断言证明窗口 frame、
  sidebar 存在和播放时间线／identity 在该尺寸保持。大文字内容的可读性与 sidebar 滚动位置
  属于缩放前断言和人工观察，不由缩放后的自动断言关闭。

测试 portability 修正包括：不再按英文 label 查找系统 Back／Sidebar，而是在当前窗口系统
Toolbar 中按受控 fixture 的按钮数量和横向位置识别；读取 fixture 文本时兼容 AX `value`
与 `label`；搜索 draft 使用不受当前输入法组合状态影响的数字串。Toolbar 的数量／位置仍是
受控 XCUI 契约，不代表系统私有 API。

第一次 Stage 10 运行还暴露了两个测试假设：拉丁字母输入被当前输入法候选窗干扰；SwiftUI
源码上的 `playback.player.container` identifier 没有出现在 XCUI 树中。最终测试没有为此
改变生产 VoiceOver 结构，也没有增加假的 player fixture。可见播放工作台由现有
`playback.destination`／sidebar 用户路径观察；player host 的唯一性与播放器连续性分别由
`PlayerHostViewIdentityTests` 和真实本地 AVPlayer timeline／identity 证据关闭。

### 860×620 不属于本阶段关闭条件

旧 spike 的 860×620 矩阵由 Debug-only `UITestWindowConfigurator` 调用
`NSWindow.setContentSize` 强制建立；它证明窗口被程序设为该尺寸后曾观察布局，但没有证明
用户能把播放中的生产窗口拖到 860 pt。旧 spike 唯一真实边缘拖动同样只到 1080×680。

Stage 10 曾尝试降低生产 `AppShellView`／detail column 的最小宽度，但签名 XCUI 仍稳定停在
1080×680，改动既没有产品裁决也没有达到目标，已完整撤销。当前结论是：1080×680 只是
本次迁移经真实拖动实证的保守验收下限，不是永久产品最小窗口契约。若产品以后要求 860，
需要单独设计 metadata、Toolbar、sidebar、播放器面积和大文字紧凑布局，不能用 test-only
`setContentSize` 代替用户可达性。

## unsigned fixture 的 Computer Use 验收

Step 9 在 signed XCUI 尚未启动时，复用最高 App Gate 产生的 unsigned Debug App，以
`-ui-testing -ui-testing-contextual-navigator -ui-testing-large-text` 启动。Computer Use
每次从新的 AX 状态读取稳定 element，再执行一个语义动作；没有把最终截图或真实内容写入
仓库。

观察结果：

1. 初始窗口只有一个真实 `NavigationSplitView`、一个系统 sidebar toggle、热门来源和
   detail；没有自定义重复 toggle。
2. 从热门进入播放后，同一 sidebar 列原位切换为合成评论；detail 显示实际
   `AVPlayerView` 控件和系统 Back。
3. 系统 hide/show 实际移除并恢复 sidebar 的可交互 AX 子树；detail 和 Back 保持。
4. A → B → C 的 `playerIdentity` 保持不变，播放 generation 为 1 → 2 → 3，旧 item
   依次成为 `lastStopped`；任一时刻 `activeItems`、`activeObservers` 和
   `activeMediaDirectories` 均为 1，没有形成嵌套 Back 层级。
5. 同 BVID 从 P1 切到 P2 后 player、item 和 generation 不变，时间线继续推进。
6. 窗口从宽布局缩到紧凑布局后，混合中文／English／日本語和两级回复仍可读；sidebar
   与 player 均只有一个可见 surface。该手动观察不替代 signed XCUI 已关闭的
   1320×820 → 1080×680 精确窗口 frame 断言，也不证明 860×620 用户可达。
7. 系统播放器全屏实际进入并退出；返回窗口后仍是同一 player identity。
8. 从播放页执行系统 Back 后，来源 sidebar 恢复，item、observer、时间线和临时媒体目录
   归零。
9. 搜索 draft `fixture draft`、结果工作集在播放往返后恢复；热门和观看历史也分别完成一次
   进入播放／Back。当前 fixture 历史路径明确是显式 UITest 身份，不是生产登录能力。
10. 播放中关闭窗口后，新 materialize 的窗口读取进程级资源计数为 0，旧 owner 没有被新
    owner 的局部状态掩盖。

透明 telemetry 只用于读取测试 owner 的 identity、generation 和清理计数；真实 sidebar、
Toolbar、Back、AVPlayer 控件、全屏和窗口布局的可见结论均来自实际 AX 树和可见窗口。

## 真实游客 production composition

同一 unsigned Debug App 不带 UITest 参数启动，使用公开游客网络路径。未进入账号、二维码
或登录历史；验证记录不保存 BVID、CID、视频标题、正文、完整远端 URL、用户标识或凭据。

观察结果：

1. 真实热门工作集加载；从一项热门进入同窗口播放后，生产 sidebar 明确显示“评论尚未
   接入”，没有合成评论或推荐泄漏到 production。
2. AVPlayer 时间线从 0 前进到 43 秒以上。期间执行 sidebar hide/show 和一次窗口
   resize，时间线持续前进，没有出现第二个 player surface 或回到 0。
3. 播放期间只统计该 App 进程的 TCP 句柄，观察到一个
   `127.0.0.1` loopback listener；系统 Back 后 `tcpRows=0`、
   `loopbackListeners=0`。
4. Back 后热门工作集仍存在，没有重新落到空白根页面。
5. 游客搜索 `SwiftUI` 得到真实工作集；进入结果后在“正在准备播放”阶段立即 Back，搜索
   draft 和结果恢复，随后 `tcpRows=0`、`loopbackListeners=0`，没有迟到 load 重新留下
   listener。
6. `Command-Q` 后受控 App 进程正常退出。

unsigned production composition 的启动日志出现 Swift Debug dylib／Package framework
重复加载部分 `BiliNetworking` class 的 Objective-C runtime warning。本轮没有出现对应
crash 或 cast failure；该 warning 不是导航 assertion，也不能由本次可见观察判定为已解决。

以下项目仍未关闭：

  基本操作，不等于发布闭环；
- 860×620 及更窄窗口、分屏、多语言极端文本和真实内容的产品适配；
- XCUI 尚未覆盖的真实焦点顺序和隐藏 sidebar 非交互边界；
- 真人 VoiceOver 阅读顺序、label／value／hint 质量和 Full Keyboard Access；
- 登录态真实观看历史、扫码登录与窗口重启恢复；
- 真实相关推荐 A → B，因为当前没有获批生产 caller／endpoint；
- 真实评论位置，因为当前没有可靠生产 comments model／endpoint；
- Intel、其他 macOS 版本、远程 CI 和多窗口压力；
- Instruments 级泄漏或性能结论。一次 AX／`lsof` 观察不能替代这些证据。

## 结论

当前 `NavigationSplitView` 迁移在本机可执行范围内满足稳定两栏、上下文 sidebar、系统
Back、单一 player host、来源状态恢复、A → B 原位替换和退出清理目标。三条决策型 signed
XCUI 已通过；1080×680 是当前真实拖动实证下限，860×620 明确留作产品决策而非迁移阻塞。

后续若改变 Bundle Identifier、Team、签名环境或系统版本，应重跑 signed Keychain smoke
和同三条决策型 XCUI；旧 access group 登录态按不可迁移处理。不能为了尺寸或签名断言改变
导航／媒体所有权。若未来接入真实 comments／recommendations，必须另行建立 production
model、caller、安全边界与验证，不能把本次 fixture 直接搬入生产。
