# M5.0 日用客户端状态保留与缓存决策

> Revision：D2。状态：预确认红区终审未发现剩余 blocker，等待用户确认；不授权
> 生产实现、新 endpoint、
> 磁盘持久化或通用缓存框架。

## Goal

让用户在同一窗口内从当前热门或最后一次搜索切到其他一级入口、进入视频再返回时，
立即看到离开前的内容、选择与可恢复滚动位置，不因普通导航重复请求；同时用明确刷新、
上限和清理规则避免旧请求回流与 Browse 工作集无界增长。未来首页个性推荐、History
总量、图片和磁盘缓存不在本切片内。

## Context

当前行为由代码直接决定：

- `ContentView.feedTaskID` 随一级 route 切换；热门激活时调用
  `loadPopular(pageSize: 50)`，历史或无提交搜索时调用 `feedModel.cancel()`。
- `GuestFeedViewModel.cancel()` 会取消 Task、递增 generation，并把唯一 `state`
  重置为 `.idle`；热门与搜索共享这一个状态槽。
- 返回热门后 `.task(id:)` 再次执行，因此会重新请求并显示全屏 loading。
- 正式 API transport 使用 ephemeral session，显式设置 `urlCache = nil` 和
  `reloadIgnoringLocalCacheData`。Repository 与 Use Case 也没有响应缓存。
- `AsyncImage` 没有项目自有、可测量和可清理的图片缓存契约；不能把可能存在的系统
  行为写成产品保证。
- WBI key、弹幕三段与当前播放链路中的局部缓存服务各自协议或媒体生命周期，不构成
  页面内容缓存。
- `AppReturnSnapshot` 目前只保存来源 section、搜索词和选中 BVID，没有滚动 anchor。
- `WatchHistoryViewModel.deactivateRoute()` 已展示了可复用语义：离开 route 时取消
  临时任务，但保留成功加载的数据；登出和窗口关闭才执行完整 reset。

## 最小日用客户端必须具备的状态能力

| 能力 | v1 最小行为 |
| --- | --- |
| Browse 工作集 | 热门／最后搜索的普通 tab 往返不清空已加载内容，不自动重复请求 |
| 返回连续性 | 视频返回后恢复来源、最后选中项和稳定 item anchor，而非精确像素 |
| 明确刷新 | 用户刷新一定发起新请求；刷新期间保留旧内容，失败不清空可用内容 |
| 新旧结果隔离 | route、query 或来源变化后，旧请求不能覆盖当前状态 |
| 有界保留 | 热门最多一页 50 项；搜索只留最后一个 query 的一页；各一个 snapshot |
| 失效边界 | 窗口关闭清空 Browse 工作集；本切片不新增认证／个性化状态 |
| 网络退化 | 有旧内容时展示 stale 内容与刷新错误；无内容时才进入完整失败状态 |
| 可观察性 | 测试能统计请求次数、两个 snapshot 上限和清理结果，不记录真实内容身份 |

这些能力不等于“把所有响应保存到磁盘”。页面状态、响应缓存、图片缓存、媒体缓存与
持久化是五个不同问题，必须分别决定。

## 推荐决策

### D1：当前每窗口单一 Browse owner 保留两个 snapshot

继续由 `ContentView` 每窗口持有的单一 Browse ViewModel 负责当前热门与搜索请求；
现有类型名是 `GuestFeedViewModel`，M5.0 为保持切片边界默认不改名，但它不是未来首页
最终 owner，也不得吸收个性推荐。该 ViewModel 内部只增加：

- 一个热门 snapshot；
- 一个最后搜索 snapshot，query 改变时替换；
- 一个当前请求 Task、一个 generation 和一个 active request identity；
- 每个 snapshot 的 refreshing／refresh error、最后选中 item 与稳定滚动 anchor。

App 层继续只拥有 route、播放开始／停止和返回意图，不保存视频数组或 endpoint DTO。
Application port 与 API adapter 保持无缓存语义。首个切片只覆盖已有热门与最后一次有效
搜索；未来首页个性推荐必须使用独立 source identity，并在 App／Web 来源决策后定义
自己的分页和登录 scope。

`ContentView.task(id:)` 只把激活意图交给 ViewModel；内部 Task 是唯一网络工作 owner。
route/query 激活先递增 generation 并取消旧请求，再决定是否首载。进入 `.none` 时调用
`deactivate`，关窗调用 `reset`；外层 Task 取消不被当成内部请求已经清理的证据。

离开 route 时执行 `deactivate`：取消尚未完成的请求，但保留两个成功 snapshot。
再次进入时：

1. 有 snapshot：立即显示，不因 tab 往返自动请求；
2. 无 snapshot：执行首次加载；
3. 用户刷新：递增 generation、取消旧请求，保留旧内容并执行唯一新请求；
4. 刷新失败：保留旧内容并显示非阻断错误。

`deactivate`、route/query 替换和取消必须同步推进 generation、清除 active request，
并将与该 request identity 匹配的 snapshot `refreshing` 归零；取消本身不产生
refresh error。只有 snapshot 的 surface/query identity 与失败请求完全一致时，才能
作为刷新失败 fallback。搜索 A 成功后首次加载新 query B 若失败，必须显示 B 的失败态，
不能在 B 标题或 query 下继续展示 A 的结果。

Phase 1 不引入 `loadedAt`、TTL、注入时钟、自动后台 revalidate 或前后台刷新。未来
个性推荐的刷新时机由后续独立设计决定，不能借本切片隐藏 tab 重复请求。

### D2：首个切片只做内存工作集，不做磁盘内容缓存

- 热门最多保留当前一页（现状上限 50 项）和一个 snapshot。
- 搜索只保留最后一次已提交 query 的当前页和一个 snapshot，不建立多关键词 LRU。
- 历史继续由自身 ViewModel 管理，不复制进 Browse 工作集；History 总量上限不由
  本契约证明，后续另立窄切片。
- 窗口关闭释放两个 Browse snapshot；App 重启重新加载。
- 本切片只有公共热门与搜索，不增加 auth epoch。未来个性推荐出现真实调用方时，再
  定义不可反查账号的认证 generation 与登出顺序。

若未来需要跨启动恢复，必须另立本地持久化与隐私契约，确定 schema、期限、容量、
迁移、手动清除和登出语义；不能把内存 snapshot 直接编码进 `UserDefaults`。

### D3：图片缓存是未验证的后续问题，不属于本次授权

本切片不替换 `AsyncImage`，也不对它的缓存、落盘或淘汰作保证。只有状态保留完成后，
真实卡片往返仍能稳定复现重复下载、解码抖动或内存问题，才重新进入决策价值 Gate：
先测当前系统路径；仍需替代时，最多比较一个有明确成本上限的候选。当前系统路径已经
满足体验与资源边界时立即停止，不创建自定义图片框架、磁盘 schema 或第三方依赖。

### D4：不增加通用媒体缓存

AVPlayer、loopback bridge、字幕与弹幕继续按当前播放 identity 管理短生命周期数据；
切视频、返回与关窗保持资源归零。v1 不以“缓存”名义增加离线媒体、DASH 分段持久化、
预下载或后台下载；这些属于下载／媒体持久化非目标。

## Owner、不变量与清理

| 边界 | Owner | 不变量 | 清理点 |
| --- | --- | --- | --- |
| route 与播放返回 | `AppNavigationModel` | 唯一一级 route；不持有页面 payload | 关窗清空 |
| Browse 工作集 | 每窗口单一 Browse ViewModel（当前名 `GuestFeedViewModel`） | 热门与最后搜索各至多一个 snapshot | 关窗 reset |
| 网络请求 | 同一个 Browse ViewModel | 当前热门／搜索合计至多一个 active request；旧 generation 不覆盖 | route/query 激活、deactivate、refresh、reset |
| 历史 | `WatchHistoryViewModel` | 与 Browse snapshot 不复制 | 登出、认证失效、关窗 |
| 图片 | 当前系统路径 | 缓存与内存行为未由本契约证明 | 后续按证据另立契约 |
| 播放／字幕／弹幕 | 现有 playback identity owner | 不因页面 snapshot 保留播放器或媒体任务 | 切视频、返回、关窗 |

Browse snapshot 可以在当前窗口进程内短暂持有卡片所需领域展示值，包括 BVID、标题、
封面／头像的公共 HTTPS URL、作者和统计信息；否则无法恢复页面。它们不得进入磁盘、
`UserDefaults`、日志、probe、验证记录或截图元数据。snapshot 不得持有 View、
播放器、Task、URLSession、Cookie、response body、授权 URL、跟踪 URL 或媒体对象。
未来推荐若出现动态授权／跟踪 URL，由后续独立契约另审。

热门／搜索各自的 snapshot 持有当前可见稳定 item identity。普通 tab 往返直接使用
Feature anchor；打开视频时，现有 `AppReturnSnapshot.selectedBVID` 同时作为最低成本
返回 anchor，App 不复制数组。Phase 1 不承诺 History 的选中态或滚动恢复。

## 明确拒绝

- 用当前“热门”作为未来首页个性推荐的缓存 fallback。
- 在 `BiliNetworking` 增加无业务语义的全局字典或 `CommonCache`。
- 让 `AppNavigationModel` 保存页面数组、分页 cursor 或网络错误。
- 为解决 tab 重载直接开启整个认证 API session 的 `URLCache`。
- 首个切片同时实现内存状态、磁盘数据库、图片 pipeline、预取和后台刷新。
- 把播放器、字幕、弹幕或 loopback server 留在缓存中以换取“秒开”。

## 决策价值 Gate

本契约只支持两个决策：

1. tab／播放返回的最小修复是否应采用 Feature 工作集保留，而不是 Repository 或磁盘
   响应缓存；
2. 状态保留完成后，是否仍有证据需要为图片问题重新立项。

能改变下一步的结果：

- 如果工作集保留已经消除重复 API 请求与页面闪烁，停止扩张数据缓存。
- 如果真实图片请求、解码或 RSS 仍造成可重复问题，重新进入图片决策 Gate。
- 如果个性推荐来源要求与热门不同的刷新、登录或分页语义，留给后续独立设计，
  不把差异塞进 M5.0 的通用抽象。

## 复杂度预算

Phase 1 状态保留：

- 零新 target、Package、endpoint、schema、数据库、actor、runner 和第三方依赖；
- 最多两个新的 Feature state/value 类型；仍只有一个 ViewModel、Task 和 generation；
- 一个现有 stub 扩展请求计数，不新增 probe executable；
- 一条 App fixture 路径覆盖热门 → 搜索假值 → 热门 → 搜索 → 播放 → 返回 → 手动刷新；
- 只固定热门当前页、最后搜索和稳定 item anchor，不开发通用多页 cache。

图片问题不计入本契约实施预算。若 Phase 1 后仍可重复，另立契约时以当前系统路径为
基线，最多增加一个替代候选；不得直接沿用 D1 作为图片生产授权。

## 分阶段实施与 Gate

### Phase 1A：状态语义

- 将“取消并清空”拆成 `deactivate` 与 `reset`。
- 为热门和最后搜索建立互不覆盖的 snapshot。
- 加入保留旧内容的显式刷新、请求去重与 generation 测试。

Gate：

- 热门 → 历史 → 热门不增加 repository call，内容仍在；
- 手动刷新恰好增加一次 call，旧内容在刷新期间可见；
- 刷新失败保留旧内容，后发 route/query 不被旧结果覆盖；
- 延迟请求在热门 → 搜索 → History 后迟到不能回填；
- 刷新中关窗、连续刷新、旧 query 迟到和 reset 后迟到不能复活 snapshot；
- 刷新中 deactivate 后返回不保持 busy，取消不产生 refresh error；
- 搜索 A 成功后搜索 B 失败不显示 A 的 snapshot；
- reset 后两个 snapshot 与 Task 归零。

### Phase 1B：返回与有界资源

- 用稳定 item identity 恢复热门／搜索列表 anchor；不承诺精确像素或 History 恢复。
- 固定热门一页 50 项、最后搜索一页、各一个 snapshot，不实现分页淘汰。
- App fixture 覆盖 tab 往返、视频返回、刷新和关窗。

Gate：

- 返回后无需重新请求即可看到离开前卡片与选中状态；
- 关闭窗口后无 Browse Task、snapshot 或播放资源残留；
- Package/App Gate 与 M4 播放生命周期回归通过。

### 后续条件：图片与 History 上限

图片行为和 History 累积上限均保持“未验证”，不能由 M5.0 Gate 推断。只有真实问题
具有决策价值时分别建立窄契约，不与 Browse tab 修复捆绑。

## Done when

- 独立红区审查没有 lifecycle、隐私、无界资源或错误失效 blocker；
- 用户确认 D1 单 Browse owner 双 snapshot、D2 不做磁盘内容缓存，以及图片／History
  不在本次生产范围；
- 实现后最高适用 App Gate 通过；
- 确定性测试证明请求次数、旧结果隔离、刷新失败保留、上限与清理；
- 一条无个人数据真实 UI 路径证明 tab／播放返回不闪回 loading、刷新可发现；
- 文档明确记录图片实际缓存、History 总量与个性推荐刷新语义仍未验证。
