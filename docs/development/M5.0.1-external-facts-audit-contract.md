# M5.0.1 外部事实全面审计执行契约

状态：已完成的历史执行契约；2026-07-27 获用户批准，2026-07-29 完成审计、裁决与
授权修复。本文件只解释当时证据等级、工作边界和 Gate，不决定当前实施顺序。

## 1. 目标与非目标

M5.0.1 不以“找到更多可改代码”为目标，而是重新核对 BiliKit 所依赖的外部事实，识别：

- 已经过期或只被本地 fixture 支持的协议假设；
- Apple、标准库或系统框架已经提供，而项目仍自行实现的能力；
- 有真实安全、平台或可替换实现边界的抽象，以及只有转发作用的结构噪音；
- 为历史症状加入、但根因变化后仍遗留的 workaround；
- 超出实际证据强度的测试、文档与路线图声明。

审计阶段只生成事实清单、证据索引和最小验证建议。不得顺手修改生产代码、测试预期、
安全策略、路线图完成状态或架构门禁；修复路线必须等审计基线冻结、交叉复核和用户裁决后
另行制定。

下载、转码、媒体导出、直播、多账号、区域解锁、DRM 绕过和复杂写操作仍不在范围内。

## 2. 基线与工作区隔离

正式开始时由主 Agent 记录并冻结以下基线：

- 生产基线：`origin/main` 的完整 SHA、提交时间、Xcode／Swift 版本、最低系统版本、
  Package targets、App target、entitlements 和依赖锁定状态；
- 工作树：审计分支必须从该 SHA 创建且干净。其他 worktree 的未提交内容不进入基线，
  不得被审计 Agent 修改、暂存或删除；
- 当前事实：PR #18 已合并，WBI 字幕目录修复已在生产基线中；不存在待审计的“未提交字幕
  diff”。审计对象改为合并后的实现、其 Git 历史，以及已经删除的启发式重试方案所对应的
  原始症状与裁决过程；
- 参考仓库：只位于被 Git 忽略的 `references/`。使用前记录 remote、完整 commit SHA、
  commit date、最近活动、dirty 状态和 license；不得成为 target、fixture 或发布内容，
  不得复制第三方源码；
- 现场证据：只保存脱敏的请求结构、状态码、响应形状、时间和结论，不保存 Cookie、
  token、QR key、完整 URL、完整响应、个人历史或账号内容。

本次整理时的候选基线为 `origin/main`
`a00744639f853ffbd7543a56c29a1588d41d93ea`。正式审计开始前必须重新读取，不把该 SHA
永久写成当前真理。

## 3. 证据优先级与结论强度

所有发现严格按以下顺序取证：

1. Apple 官方文档、SDK interface、WWDC、HIG，以及 RFC、ISO BMFF、HLS Authoring
   Specification 等原始标准；
2. 当前真实 App／服务行为和脱敏现场请求；
3. 至少两个彼此独立、仍活跃的 OSS 当前源码与提交历史；
4. 社区 API 文档、Issue 和讨论；
5. BiliKit 的 fixture、mock、测试和既有文档。

低优先级证据不能推翻高优先级证据。第 5 级只能证明实现符合项目写下的预期，不能单独
证明预期、endpoint 或平台语义正确。

每条外部事实必须记录：

```text
fact_id
主张
事实类型：规范 / 当前行为 / OSS 实现 / 社区报告 / 本地预期
来源 URL 或 SDK 路径
版本、OS、commit、日期与访问日期
原始证据的最小摘录或代码位置
适用条件与反例
证据强度：已确认 / 多源印证 / 单次观察 / 推断 / 未知
```

额外规则：

- Apple API 结论必须核对最低支持的 macOS 15 SDK interface；只查最新在线文档不足以证明
  availability。
- “当前服务行为”至少区分一次成功、可重复成功和跨样本稳定；一次现场成功不得写成稳定
  契约。
- OSS 对照必须记录文件位置以及 commit SHA/date。若找不到两个活跃且独立的实现，应写
  “证据不足”，不能用更多同源 fork 凑数。
- 搜索摘要、博客和 README 只作为线索；最终结论回到原始文档、源码、提交或真实行为。
- 相互冲突的高优先级证据不得由 Agent 自行择一，进入争议清单等待最小复现实验或用户
  裁决。

TODO 数量或重构工时估算。

## 5. 十条审计线

### 5.1 API、WBI、认证与安全策略

- 枚举所有 endpoint、HTTP method、query、header、Cookie 要求、WBI 参数、重试、
  fallback 和 response DTO。
- 对照当前脱敏请求与至少两个 OSS，核查游客、登录、历史、详情、播放地址、字幕和弹幕。
- 逐项审查 QR 生命周期、Cookie 导入与持久化、刷新、失效、登出、redirect 和 host
  allowlist。
- 白名单不得放宽为通配；任何修改候选都必须说明当前协议事实、攻击面与失败关闭方式。

### 5.2 媒体播放

- 从真实 manifest／segment 语义出发审查 DASH → HLS、SIDX、byte range、HTTP Range、
  CDN fallback、seek、替换播放项、音画同步和错误恢复。
- 分别对照 AVFoundation、RFC 8216、ISO BMFF、HLS Authoring Specification，以及
  ATV-Bilibili-demo、wiliwili、BBDown 等当前实现。
- 字幕与弹幕必须核查目录、正文、时间基准、分段、切换、seek 和错误隔离；不能只验证
  decoder 接受 fixture。

### 5.3 Swift 并发与生命周期

- 建立 Task、actor、AsyncStream／continuation、generation、timer、observer、server、
  player、renderer 和 layer 的 owner 图。
- 对页面退出、A → B → A、切分 P、登出、替换播放项、关窗和 App 退出逐条追踪创建、
  取消、迟到结果拒绝和释放。
- generation、额外 reset worker 或 timeout 只有在原始竞态可重现且无法由所有权简化时
  才能判定保留。

### 5.4 隐私、日志、redirect 与秘密

- 以 `docs/security/` 为入口复核 Keychain、内存凭据、日志脱敏、probe、fixture、
  redirect、loopback 和远端媒体来源。
- 检查错误对象、URLRequest 描述、AVPlayer access/error log、测试附件和 CI artifact
  是否间接泄露秘密或个人内容。
- 安全结论必须覆盖失败路径；“正常路径未泄露”不足以关闭发现。

### 5.5 Apple 原生 UI 与产品信息架构

- 对照 macOS 15 SDK、Apple Documentation、WWDC、HIG 和 Apple Music／TV／Podcasts
  的当前真实行为，审查 Tab、层级导航、搜索、账户入口、播放页、窗口与返回上下文。
- 枚举所有 `NSViewRepresentable`／`NSViewControllerRepresentable`、手写
  `Binding(get:set:)`、用于布局决策的 `GeometryReader`、自定义 route、格式化器、
  命令和播放器宿主。
- 每个 bridge 必须回答：“它提供了 Apple API 没有的哪项职责？”外观差异本身不能证明
  需要 bridge。

### 5.6 状态与缓存

- 分开审计 SwiftUI View state、窗口内页面工作集、请求去重、URLCache、图片加载缓存、
  媒体缓存和持久化；不得用一个 `cache` 结论覆盖所有层。
- 对每项记录 owner、identity、容量、失效、生命周期、隐私和用户可观察需求。
- 核查 `AsyncImage`、URLSession configuration、SwiftData 等原生能力，但不因 API 存在
  就推定项目需要采用。

### 5.7 Accessibility 与输入

- 用 Accessibility Inspector、VoiceOver 和真实键盘路径验证焦点顺序、标签、状态、
  Return、Escape、菜单命令、全屏、文字放大、Reduce Motion 和窗口 resize。
- 区分截图、辅助功能树、键盘自动化和 VoiceOver 实际朗读各自能证明的范围。
- 枚举所有 focus workaround、键盘监听和手写命令路由，核查是否已有 SwiftUI／AppKit
  原生表达。

### 5.8 性能与资源

- 在明确硬件、OS、构建配置和样本下记录 Instruments／xctrace、Memory Graph、
  AVPlayer access/error log 和可重复操作脚本。
- 覆盖启动、热门与搜索滚动、图片加载、首次播放、seek、字幕／弹幕、连续切视频、
  窗口 resize 和关闭后的稳定状态。
- 不以一次 trace、平均 FPS 或“看起来流畅”证明无泄漏；记录峰值、稳态、回落、卡顿和
  测量扰动。

### 5.9 架构必要性

- 生成真实 `Scene → View → ViewModel → UseCase → port → adapter → client` 调用图，
  按实际调用者而不是 ADR 或架构教材裁决。
- 对每个 Application protocol、UseCase、target 和 wrapper 记录调用者数量、实现数量、
  隔离的不稳定边界和删除后的实际变化。
- 单实现／单调用者不是自动删除条件；能够隔离平台、网络、安全、可替换实现或高价值
  确定性测试仍可保留。只有转发且没有边界才列为结构噪音候选。

### 5.10 工程与分发

- 核对 Xcode／SwiftPM、macOS 15 与 26、Swift 6 并发、签名、entitlements、Keychain
  access group、sandbox、notarization、归档和升级／卸载数据边界。
- 清点所有依赖及 reference license；reference 不等于可复制或可链接。
- 区分本地 build、测试、签名运行、归档、notarization 和真实安装，各自不得代替下一层
  证据。

## 6. 五个横向清单

第一轮扫描只建立清单，不下删除结论：

1. **Apple bridge 清单**：所有 representable、手写 Binding、GeometryReader
   布局决策、自定义导航／格式化／命令和 player host。
2. **Application 边界清单**：所有 protocol、UseCase、调用者、实现者、mock 和 target
   依赖。
3. **Workaround 清单**：自动／手动重试、固定 timeout、generation、snapshot、offset、
   合理性判断、reset worker、特殊 header 和 fallback endpoint；每项回链最初症状、
   引入 commit 和现有回归测试。
4. **安全白名单清单**：endpoint、method、query、header、Cookie、redirect、API host、
   CDN host 和 loopback。
5. **完成声明清单**：路线图、验证文档和测试名称中的每项“完成／稳定／真实”声明，以及
   它实际拥有的证据等级。

## 7. Agent 分工与写入规则

并行只用于相互独立的取证，不用于并行修改共享生产代码。最多使用三个子 Agent，加主
Agent 共四个并发槽：

### 第一轮：正确性与风险

- Agent A：API、WBI、认证、安全白名单；
- Agent B：媒体、Range、播放器、字幕与弹幕；
- Agent C：并发、生命周期、隐私、日志与 redirect；
- 主 Agent：冻结基线、建立五个横向清单、复核证据格式和冲突。

### 第二轮：原生化与简化

- Agent A：Apple 原生 UI、产品信息架构；
- Agent B：状态、缓存、Accessibility 与输入；
- Agent C：架构必要性、工程与分发；
- 主 Agent：性能实测、跨线调用图、证据交叉复核。

写入约束：

- 每个 Agent 只写自己的 `findings/` 文件或主 Agent 分配的 inventory 文件；
- `README.md`、`baseline.md`、`evidence-register.md` 和 `decision-register.md` 由主
  Agent 单写，避免并发覆盖；
- Agent 可以读取全仓库和 `references/`，不得修改生产代码、测试、路线图、ADR、
  security 文档、reference checkout 或其他 Agent 文件；
- Agent 回报必须包含准确路径、行号、commit/date 和未解决问题；不接受只有结论的摘要；
- 主 Agent 不因多数 Agent 同意就关闭争议，仍按证据优先级独立复核。

## 8. 执行阶段与 Gate

### Gate 0：基线

- 工作树、生产 SHA、工具链、targets、entitlements 和 reference SHAs 已记录；
- 审计目录和文件 owner 已建立；
- 所有现场验证的隐私边界、账号要求和停止条件已明确。

### Gate 1：完整枚举

- 十条审计线和五个横向清单都有 owner；
- 每个候选项都能回到具体符号、调用链或完成声明；
- 不允许只抽样“看起来危险”的文件后宣称全量。

### Gate 2：外部取证

- 高风险协议与媒体结论具有第 1／2 级证据，并尽可能由两个 OSS 交叉验证；
- Apple API 结论包含 availability；
- 无法取得足够证据的项目明确标为“尚不能判断”。

### Gate 3：真实验证

- 仅对会改变判断的争议运行最小现场请求、真实 UI 或 Instruments；
- 每次验证预先写明假设、可观察量、脱敏方式和停止条件；
- 不重复请求来强行得到预期结果。

### Gate 4：交叉复核

- 每条“删除／替换”和高风险“保留”结论由未撰写该条目的另一角色复核；
- 调用链、外部事实、真实行为和本地测试边界相互一致；
- 冲突进入 decision register，不在审计阶段偷偷折中。

### Gate 5：审计冻结

- 形成按风险和依赖排序的事实清单；
- 用户逐项核对关键争议和判断；
- 冻结审计 commit 后，才另建修复路线、分组 commit 和 PR。

## 9. 停止与升级条件

出现以下情况时停止对应验证并报告，不自行扩大权限或范围：

- 需要保存或展示 Cookie、token、QR key、完整认证 URL、个人历史或完整远端响应；
- 需要绕过区域、会员、DRM、风控或服务端权限；
- 必须放宽 host／redirect 白名单才能继续，但尚无高优先级证据；
- Apple 文档、SDK interface、真实行为和 OSS 出现无法解释的冲突；
- 真实请求开始影响账号、观看历史或其他服务端状态；
- Instruments、签名、Keychain 或真实 UI 需要用户交互或新的系统权限；
- 某个 Agent 发现生产缺陷；审计阶段只登记，除非用户另行授权紧急修复。

## 10. 审计后的修改路线

审计冻结后才按以下原则制定修复批次：

1. 先处理安全、凭据泄露、协议错误和媒体正确性；
2. 再处理生命周期、资源泄漏和真实可访问性阻塞；
3. 再用 Apple 原生能力替换 workaround；
4. 最后删除结构噪音、修正文档与测试声明。

每个修复批次必须引用 finding ID，保留能够复现原始症状的测试，并运行覆盖该修改的最高
质量 Gate。不得把十条审计线合并成一个不可审查的大 PR。
